> 版本：v1.0
> 日期：2026-08-19
> 优先级：P2
> 关联：product-roadmap.md F7（在线支付）、F8（营销工具）；SETUP_FEATURES.payment 开关

---

## 一、背景与目标

### 问题

当前发卡只有一条路径：馆长/教练在管理端手动发卡（`AdminCardService.issueUserCard`）。会员想买卡，必须线下付款（现金/微信转账/扫码），再由馆方手动录入一张 `ax_user_card`。这带来三个成本：

- **对账成本**：钱和卡是两个动作，靠人对齐，容易漏发、错发、发错卡种。
- **转化流失**：会员产生购买意愿的当下（比如约课时发现没次数了），没有即时下单入口，等联系上馆方，意愿已经凉了。
- **营销无抓手**：优惠券、体验课、限时折扣这些拉新留存工具，没有"下单"这个承载动作就无从谈起。

### 目标

- 会员端可自助**下单 → 微信支付 → 自动到卡**，全程无需馆方介入。
- 复用现有 `issueUserCard` 发卡链路，**不新造第二套发卡逻辑**，避免两套逻辑口径漂移。
- 为 F8 营销工具（优惠券/体验课/限时价）预留**价格计算插槽**，营销只改"应付多少"，不碰"发什么卡"。
- 收入统计口径与现有一致（基于 `USER_CARD_PRICE / USER_CARD_QUOTA_INIT`），营销优惠后收入不虚高。

### 不做什么（本期）

- **不做**平台分账 / 资金托管：本期钱直接进租户自己的微信商户号（见 §7 资金模型），平台不碰钱。分账留到 SaaS 商业化阶段。
- **不做**拼团、积分商城、分销：属于 F8 后续子功能，本期只把优惠券/体验课的价格计算钩子留出来。
- **不做**退款自动化审批：本期退款为馆长手动发起（走微信退款 API），不做会员自助退款。
- **不做**发票 / 开票：合规复杂，另立专题。

## 二、核心设计原则

### 原则 1：购卡 = 支付成功后调用现有发卡

购卡不是新功能，是给 `issueUserCard` 加一个**触发来源**。流程终点必然是"插入一条 ax_user_card"，这条逻辑已经存在且被管理端验证过。购卡链路只负责：**收钱 → 收到钱 → 调它**。

```
会员下单 → 创建 ax_order(待支付) → 微信统一下单 → 会员支付
        → 微信支付回调 → 校验 → 幂等地调 issueUserCard → 订单转"已发卡"
```

### 原则 2：营销是"价格插件"，不是"发卡分支"

优惠券、体验课、限时价，全部只影响**订单的应付金额与实付金额**，不影响"发哪张卡、发多少次/多少天"。卡的规格永远来自 `ax_card_tpl`。这样营销工具怎么加都不会污染发卡与核销逻辑。

唯一例外的语义：**实付价要写进 `USER_CARD_PRICE`**（而非模板原价），否则收入统计会按原价算，把优惠掉的钱也算成收入。见 §6。

### 原则 3：钱和卡的一致性靠订单状态机 + 幂等，绝不靠"回调只来一次"

微信支付回调会重试、会乱序、会在退款后再补发。一单发两张卡就是资损。所有"发卡"动作必须挂在**订单号唯一约束 + 状态 CAS（compare-and-set）**上：只有订单从 `PAID` 成功流转到 `ISSUED` 的那一次事务，才允许发卡。见 §5。

## 三、数据模型：新增 ax_order

沿用框架多租户约定（`_pid` 自动注入）、字段前缀 `ORDER_`、`ADD_ID/ADD_TIME` 自动填充。

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|:---:|---|---|
| `_pid` | string | ✅ | — | 租户 ID |
| `ORDER_ID` | string | ✅ | — | 业务订单号（唯一，供微信 out_trade_no 使用） |
| `ORDER_USER_ID` | string | ✅ | — | 下单会员 openid |
| `ORDER_USER_NAME` | string | — | — | 会员昵称（冗余，便于馆长端展示） |
| `ORDER_TPL_ID` | string | ✅ | — | 购买的卡模板 `CARD_TPL_ID` |
| `ORDER_TPL_NAME` | string | ✅ | — | 卡名称（下单时快照，防模板改名） |
| `ORDER_TPL_SNAPSHOT` | object | ✅ | — | 卡模板关键字段快照（type/days/quota/scope/price） |
| `ORDER_ORIGIN_FEE` | int | ✅ | — | 原价（分），来自模板 `CARD_TPL_PRICE × 100` |
| `ORDER_DISCOUNT_FEE` | int | ✅ | 0 | 优惠金额（分），营销计算得出 |
| `ORDER_PAY_FEE` | int | ✅ | — | 应付金额（分）= origin − discount，≥0 |
| `ORDER_PROMO` | object | — | — | 营销上下文快照（券 ID、活动 ID、体验课标记等） |
| `ORDER_STATUS` | int | ✅ | 1 | 订单状态（见常量） |
| `ORDER_PREPAY_ID` | string | — | — | 微信预支付会话 prepay_id |
| `ORDER_TRANSACTION_ID` | string | — | — | 微信支付单号（回调回填） |
| `ORDER_PAY_TIME` | int | — | — | 支付成功时间戳 |
| `ORDER_USER_CARD_ID` | string | — | — | 发卡后回填的 ax_user_card `_id`（发卡凭证） |
| `ORDER_REFUND_ID` | string | — | — | 微信退款单号 |
| `ORDER_REFUND_TIME` | int | — | — | 退款时间戳 |
| `ORDER_CLOSE_REASON` | string | — | — | 关闭/失败原因 |
| `ORDER_ADD_TIME` | int | ✅ | — | 下单时间戳 |
| `ORDER_EDIT_TIME` | int | ✅ | — | 最后修改时间戳 |

**金额一律以「分」存储**（int），避免浮点。展示层再 `/100`。模板里 `CARD_TPL_PRICE` 是「元」，下单时 `× 100` 转分并快照进订单。

**ORDER_STATUS 状态机：**

```
INIT      = 1   待支付（已创建订单，已下单微信但用户未付）
PAID      = 5   已支付（收到有效回调，钱到账，卡未发）
ISSUED    = 10  已发卡（ax_user_card 已生成，订单完结）—— 终态（成功）
CLOSED    = 20  已关闭（超时未付/用户取消，不可再支付）—— 终态
REFUNDING = 30  退款中
REFUNDED  = 40  已退款（卡已停）—— 终态
```

**为什么 PAID 和 ISSUED 分两个态？** 因为"钱到账"和"卡发出"是两个动作，中间可能失败（发卡时 DB 抖动）。分开后：回调只保证把订单推到 PAID；发卡是一个可重试的独立步骤，把 PAID→ISSUED。任何时刻卡在 PAID 的订单都是"已付款待补发"，可由定时任务或馆长手动补发，不丢钱。

**唯一索引**：`ORDER_ID`（业务唯一），另建 `_pid + ORDER_STATUS + ORDER_ADD_TIME` 复合索引供管理端列表查询。

**ORDER_TPL_SNAPSHOT 结构：**
```json
{
  "type": "times",
  "days": 90,
  "quota": 10,
  "scope": { "mode": "meets", "meetIds": ["..."] },
  "activate": "immediate"
}
```
> 快照的意义：会员付款那一刻的卡规格。若馆长事后改了模板（改次数、改适用范围），已付款订单必须按下单时的承诺发卡，不能按新模板发。发卡时优先用快照，模板仅作兜底。

## 四、接口设计

### 会员端

| 路由 | 方法 | 说明 |
|---|---|---|
| `user/card_shop` | GET | 在售卡列表（`CARD_TPL_STATUS=1`），含营销预展示价 |
| `user/order_create` | POST | 创建订单：入参 tplId、couponId?；出参微信支付参数（prepay 二次签名） |
| `user/order_query` | GET | 查订单状态（前端支付回来后轮询到卡与否） |
| `user/order_my_list` | GET | 我的订单记录 |

**`order_create` 核心逻辑：**
1. 校验卡模板在售、会员存在。
2. 计算价格：原价 ← 模板；调 `promoService.calcDiscount(userId, tpl, couponId)` 得优惠；应付 = 原价 − 优惠（下限 0）。
3. 幂等防重：同一会员对同一模板存在 `INIT` 未超时订单则复用，不重复建单（防连点）。
4. 落库 `ax_order(INIT)` + 快照。
5. 调微信 `unifiedOrder`（cloudPay），`out_trade_no = ORDER_ID`，回填 `prepay_id`，返回小程序 `requestPayment` 所需签名参数。

### 支付回调（云函数）

| 触发 | 说明 |
|---|---|
| 微信支付结果通知 | 云开发 cloudPay 支付回调事件，或云函数 HTTP 触发器接收 |

回调处理见 §5。

### 管理端

| 路由 | 方法 | 说明 |
|---|---|---|
| `admin/order_list` | GET | 订单列表（按状态/时间/会员筛选），对账用 |
| `admin/order_refund` | POST | 馆长发起退款（走微信退款 API，订单→REFUNDING→REFUNDED，停对应卡） |
| `admin/order_reissue` | POST | 补发卡：对卡在 PAID 的订单手动触发发卡（兜底运维入口） |

## 五、支付回调与幂等发卡（最关键）

这是整个功能唯一会造成资损的地方，单独展开。

### 回调处理流程

```
收到微信支付回调
 1. 验签（微信签名校验）——失败直接丢弃
 2. 按 out_trade_no 查 ax_order
      订单不存在 → 记日志告警，返回成功（避免微信无限重试）
 3. 校验金额：回调 total_fee === ORDER_PAY_FEE ——不等则告警，不发卡
 4. 幂等推进状态：
      CAS: UPDATE ax_order SET status=PAID, transactionId=.., payTime=..
           WHERE ORDER_ID=? AND status=INIT
      - 更新到 1 行 → 首次有效回调，继续第 5 步
      - 更新到 0 行 → 已处理过（重复回调）或状态非法，直接返回成功
 5. 发卡（见下）
 6. 返回微信"成功"应答
```

### 幂等发卡

发卡同样用 CAS 卡住，保证一单只发一张：

```
CAS: UPDATE ax_order SET status=ISSUED WHERE ORDER_ID=? AND status=PAID
  - 抢到（1 行）→ 调 issueUserCard(用订单快照)，把返回的 userCardId 回填订单
  - 没抢到（0 行）→ 说明别的回调/补发任务已发卡，跳过
```

> 注意顺序：**先 CAS 抢 ISSUED，再发卡**。若反过来（先发卡再改状态），发卡成功但改状态前进程崩溃，重试会再发一张。先抢状态即使发卡失败，也只是卡在 ISSUED 但无卡，由 `order_reissue` 兜底补——宁可漏发可补，不可重发资损。

> 对 `issueUserCard` 的适配：现有它是给管理端用的，入参有 coachId/coachName/memo/activate。购卡调用时传 `tplId`、`userId`、`activate`（取快照）、`memo="在线购卡"`，coach 相关留空。需要把内部对 `global.PID` 的依赖确认清楚——回调是无会话上下文的，必须由订单的 `_pid` 显式设置 `global.PID` 后再调（prevPid/finally 模式，与超管跨租户操作一致）。

### 未支付订单的收尾

- 会员下单未付：INIT 订单超时（如 15 分钟）由定时任务关闭 → CLOSED，并调微信关单，防止用户事后又付。
- 已付未发卡（PAID 滞留）：定时任务扫描，重试发卡；连续失败则告警馆长，走 `order_reissue`。

## 六、与收入统计的衔接

现有收入口径（data-model-reference.md ax_user_card_log）：

- 次数卡：`amount = 卡价格 / QUOTA_INIT × TIMES`
- 期限卡：首次上课那条记 `amount = 卡价格`

其中"卡价格"取自 `USER_CARD_PRICE`。所以**购卡发卡时，`USER_CARD_PRICE` 必须写实付价（`ORDER_PAY_FEE / 100`），不是模板原价**。否则一张原价 1000、用券实付 800 的卡，会按 1000 摊入收入，营销季收入全线虚高，对账对不平。

- `issueUserCard` 当前用 `tpl.CARD_TPL_PRICE`（原价）。购卡路径需传入 `priceOverride = 实付元数` 覆盖。
- `QUOTA_INIT` 仍取模板次数（发的次数没变，只是便宜卖了），保证单次分摊 = 实付 / 次数，符合真实客单。
- 体验课（0 元或极低价）同理，`USER_CARD_PRICE` 记实付，收入如实反映为"引流成本价"。

## 七、资金模型与多租户（合规关键）

**本期方案：租户自有商户号（钱不过平台）。**

- 每个 `ax_tenant` 配置自己的微信支付商户号（新增字段 `TENANT_MCH_ID` 等，或独立 `ax_pay_config` 表按 _pid 存密钥）。
- 会员付款直接进该租户商户号，平台不碰资金，规避二清（无证聚合支付）合规风险。
- 缺点：每个馆要自己申请微信商户号，接入门槛高；平台无法抽佣。

**未来（SaaS 商业化）：平台服务商 + 特约商户分账。** 平台做微信支付服务商，各馆作为特约商户进件，平台按比例分账抽取 SaaS 服务费。此时 `ax_order` 需扩展分账字段。本期不做，但表结构与状态机已为其预留（金额分字段、订单快照）。

> **落地前必须确认**：本期上线的馆是否都已有微信商户号？若目标是"零门槛开馆即卖卡"，则绕不开服务商分账，方案要提前切到未来态。这决定了本期是否只是半成品，请产品先拍板。

## 八、营销工具挂载点（F8 预留）

营销全部作用于 `order_create` 的**价格计算阶段**，通过一个 `promoService.calcDiscount(ctx)` 统一出口：

| F8 子功能 | 如何挂载 | 对订单的影响 |
|---|---|---|
| 优惠券 | 入参 couponId，校验归属/有效期/门槛，算减免 | 写 ORDER_DISCOUNT_FEE、ORDER_PROMO.couponId；发卡后核销券 |
| 体验课 | 特殊卡模板 + "每人限一次"校验（查该会员该模板历史订单） | 应付=低价/0；ORDER_PROMO.trial=true |
| 限时价 | 活动时间窗内模板价打折 | 减免计入 discount |
| 拼团 | 独立 ax_group_buy 编排，成团后批量创建 PAID 订单触发发卡 | 复用发卡链路，订单来源标记为 group |
| 推荐有礼 | 发卡成功事件里给推荐人加次数（另一张卡的 manual_add） | 不改本订单，监听 ISSUED 事件 |

关键：**这些都不新增发卡路径**，优惠券核销、限购校验都发生在下单前的价格计算或下单校验里，发卡端只认订单快照。

| 阶段 | 范围 | 交付 |
|---|---|---|
| **P0 最小闭环** | ax_order、下单、微信支付、回调幂等发卡、我的订单、管理端订单列表 | 会员能自助买卡到账，馆长能对账 |

| **P3 商业化** | 服务商分账、平台抽佣 | SaaS 变现（依赖资质，另立项） |

## 十、待决策清单（写代码前必须拍板）

1. **资金模型**（§7）：本期是"馆自有商户号"还是直接上"服务商分账"？——决定合规路径和能否零门槛开馆卖卡，影响最大。
2. **支付通道**：用微信云开发 cloudPay，还是自建微信支付 v3 + 云函数 HTTP 触发器接回调？cloudPay 接入快但灵活性/多商户支持需先验证。
3. **退款粒度**：是否允许部分退款/已用次数按比例退？本期建议只做"未使用整卡全退"，用过即不可退。
4. **超时时长**：INIT 订单多久自动关闭（建议 15 分钟，与微信订单有效期对齐）。
5. **体验课限购口径**："每人一次"是按模板算还是按"体验课"标签算？跨模板的多张体验课如何限。
