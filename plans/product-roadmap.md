## 三、P0：上线前必做

### T1 · 密码加密存储 ✅ 已完成

**问题**：管理员密码曾明文存 DB，一旦数据库泄露所有账号即暴露。  
**方案**：密码做 `SHA256(pwd + salt)` 后存储，哈希值带 `sha256:` 前缀；旧明文数据在校验时兼容（`verifyPwd` 检测无前缀则按明文比对），无需一次性迁移。

实现：`cloudfunctions/cloud/project/utils/pwd_util.js`
```javascript
function hashPwd(pwd, salt) {
  return "sha256:" + crypto.createHash("sha256").update(String(pwd) + String(salt)).digest("hex");
}
function verifyPwd(pwd, stored, salt) {
  if (!stored) return false;
  if (isHashed(stored)) return hashPwd(pwd, salt) === stored; // 新数据
  return String(pwd) === String(stored);                       // 旧明文兼容
}
```

字段：`ax_admin.ADMIN_PWD`（哈希）、`ax_admin.ADMIN_PWD_SALT`（随机盐）。创建/改密走 `hashNewPwd()`。

### T2 · 约课并发超报修复

**问题**：`join` 接口查名额和写入不是原子操作，极端并发下可能多人抢到最后一个名额。  
**方案**：利用云数据库的 `update.where._count` 原子条件更新，或在 timeMark 上加分布式锁（借助 ax_cache 实现）。

```javascript
// 伪代码：乐观锁方案
const result = await DayModel.updateWhere(
  { DAY_MEET_ID: meetId, 'times.mark': timeMark, 'times.$.stat.succCnt': ['<', limit] },
  { '$inc': { 'times.$.stat.succCnt': 1 } }
)
if (result.updated === 0) throw AppError('名额已满')
```

## 四、P1：短期迭代（3个月内）

### F1 · 储值卡（余额卡）

**背景**：当前只有次数卡和期限卡，市场上很多馆使用充值余额模式（充 3000 元，每节课扣 X 元）。  
**价值**：拓宽卡务场景，提升客单价，减少馆长的次数管理负担。

**新增字段（ax_card_tpl / ax_user_card）：**
```
CARD_TPL_TYPE 新增值：balance（余额卡）
USER_CARD_BALANCE      // 当前余额（分，避免浮点）
USER_CARD_BALANCE_INIT // 初始余额
```

**扣费规则**：预约时按 `MEET_STYLE_SET.cardAmount`（元/次，当前已有此字段但未启用）从余额扣减。

**统计改造**：收入计算 `buildIncomeEntries` 新增余额卡分支，每次扣款即为一次收入条目。

**改动范围**：`card_tpl_model.js`、`user_card_model.js`、`user_card_service.js`（_listUsableCards/consumeForJoin/refund）、前端选卡展示。

---

### F2 · 微信订阅消息推送

**背景**：预约成功、课前提醒、取消通知、卡即将到期——这些节点会员需要主动提醒。  
**价值**：减少爽约率，提升到课率，降低馆长人工通知工作量。

**推送节点规划：**

| 触发事件 | 推送对象 | 消息模板 |
|---|---|---|
| 预约成功 | 会员 | 课程名、上课时间、地点 |
| 课前 1 小时 | 会员 | 课程名、时间提醒 |
| 预约被取消 | 会员 | 课程名、取消原因 |
| 会员卡剩余 ≤ 3 次 | 会员 | 卡名、剩余次数 |
| 会员卡 7 天后到期 | 会员 | 卡名、到期日 |
| 新预约通知 | 教练 | 学员名、课程、时间 |

**实现方案**：云函数定时触发器（每小时）+ 课前提醒列表查询 ax_join（status=1, joinStartTime 在 [now, now+1h]）。

---

### F3 · 班级/课包预售

**背景**：很多馆有「8节正念冥想班」「12节产后修复课程」这类固定组合，目前无法表达。  
**价值**：提前锁客，改善现金流，适合开设系列课程的馆。

**方案**：新增 `ax_class`（班级）集合，一个班级关联多个 ax_meet 时段，单独发班级卡（类型 `bundle`），预约时匹配班级卡而非通用卡。

---

### F4 · 会员健康档案与标签

**背景**：瑜伽馆需要了解会员的身体状况（有无腰椎问题、是否孕期等），现在 ax_user 字段太少。  
**价值**：支持教练个性化授课，降低运动风险，提升专业形象。

**新增内容：**
- `ax_user` 扩展字段：`USER_BIRTHDAY`、`USER_GENDER`、`USER_HEALTH_NOTE`（健康备注）、`USER_TAGS`（标签数组）
- 会员端「我的」页面增加健康信息填写
- 教练端会员详情页展示健康备注（教练角色可见，不对其他会员展示）
- 支持馆长自定义标签（`ax_setup.SETUP_USER_TAGS`）并批量打标

---

### F5 · 预约等候队列

**背景**：热门课程满员后会员无法预约，只能等馆长通知，体验差。  
**价值**：提升满员课程的利用率，减少馆长人工沟通成本。

**方案**：
- `ax_join` 新增 `JOIN_STATUS: 5`（候补中）
- 满员时提示「已加入候补，共 N 人候补」
- 有人取消时自动通知第一位候补会员（订阅消息），给 30 分钟确认窗口
- 超时未确认则顺移至下一位候补

---

### F6 · 周课表定期复制

**背景**：现在每周必须手动重新排课，重复工作量大。  
**价值**：馆长每周只需检查并微调，节省 80% 排课时间。

**方案**：
- 排课界面新增「复制本周课表到下周」按钮
- 调用 `admin/schedule_copy_week` 接口，遍历当周 ax_day 数据，日期 +7 天后批量插入
- 支持选择性排除某几天（如节假日）

## 五、P2：中期迭代（3-6个月）

### F7 · 在线支付集成

**背景**：当前 `SETUP_FEATURES.payment` 开关已存在但功能未实现，是明确规划的方向。  
**价值**：实现闭环消费，减少现金收款的对账成本。

**方案**（详见 [f7-card-purchase.md](./f7-card-purchase.md) 完整设计）：
- 会员端自助下单 → 微信支付 → 支付回调**复用现有 `issueUserCard` 自动发卡**，不新造发卡逻辑
- 后端新增 `ax_order` 订单集合，状态机：待支付(INIT)→已支付(PAID)→已发卡(ISSUED)，另含关闭/退款态
- **幂等**：订单号唯一 + 状态 CAS，杜绝回调重试造成一单发两卡的资损
- 实付价（含优惠）写入 `USER_CARD_PRICE`，保证收入统计不虚高
- 退款走微信退款 API，馆长端增加订单/对账/退款视图
- 营销工具（优惠券/体验课）作为下单前"价格插件"挂载，不污染发卡与核销

**注意**：需要微信商户号，涉及资金合规。资金模型（馆自有商户号 vs 平台服务商分账）需产品先拍板，见文档 §7、§10 待决策清单。

### F15 · 平台操作审计日志 ✅ 已实现

**背景**：馆级已有 `ax_log`，但超管跨租户的操作（建馆/删馆/改到期/启停馆/加员工）散落在各馆 `_pid`（或漂到 `'ONE'`），删了个馆查不到谁干的，规模化后是合规硬伤。

**方案**：新增 `ax_platform_log` 集合，固定 `_pid = "PLATFORM"`，不随 `global.PID` 漂移。统一入口 `BaseAdminService.insertPlatformLog(action, operator, extra)` 写结构化字段：操作人快照（ID/名/手机/角色）、动作码、目标租户 pid+名、变更前后值。5 个超管动作在原有 `insertLog` 旁**追加**调用（不破坏馆级日志现状）；馆长在本馆加教练不算平台级操作，不记入。

查询接口 `admin/platform_log_list`（超管专用，复用 `cmpt-comm-list` 分页），前端页 `pages/admin/platform/audit_log`，删馆等高危动作标红。

实现：`platform_log_model.js`、`base_admin_service.js`、`admin_tenant_service.js`（查询 + 建馆/删馆/改期/启停）、`admin_mgr_service.js`（加员工）。

---

### F16 · 租户健康度看板 ✅ 已实现

**背景**：`getPlatformOverview` 只聚合了馆数量和 admin 数，缺"哪些馆快死了"的视角，无法支撑续费转化和主动运营。

**方案**：`admin/platform_health` 用 `mustPID=false` 跨租户拉取 `ax_tenant`/`ax_join`/`ax_user`，内存按 `_pid` 分组。口径完全复用现有逻辑（`_joinActivityTime` = `JOIN_START_TIME||JOIN_ADD_TIME`、`JOIN_STATUS=SUCC`、`tenantExpireUtil.isExpiringSoon`）。三类风险：

| 风险 | 判定 |
|---|---|
| 僵尸馆 | 运营中但近 30 天零预约 |
| 到期预警 | 即将到期 / 已到期（未主动停用） |
| 增长停滞 | 有会员基数但本月零新增 |

前端在超管首页概览 tab 顶部三格摘要卡（有风险标红），点击弹层看该类馆明细并可一键进入该馆管理。

**规模隐患**：当前对 `ax_join`/`ax_user` 做 20000 条上限的全量拉取，租户规模大幅增长后需改分组聚合或加缓存（代码已用 size 上限兜底，无静默截断）。

实现：`admin_tenant_service.js` `getPlatformHealth()`、`admin_home.js/.wxml/.wxss`。

代码侧已增加索引检查路由和推荐清单；生产环境的复合索引仍需在微信云开发控制台建立并验证，不能仅依赖云函数自动创建。

**建议建立的索引：**

### T5 · 接口响应缓存

当前首页数据（Banner/公告/教练）每次请求都全量查 DB。

**方案**：利用 `ax_cache` 集合（已存在）对 `home/index`、`home/setup_all` 结果缓存 5-10 分钟，管理员修改内容后主动失效缓存。

---

### T6 · 会员卡收入分摊精度优化

当前期限卡只在「首次上课」那条流水计入整卡金额，如果用户在有效期内没上课则无收入记录。

**改进方案**：引入「期限卡按天分摊」模式（可选），将卡价格均摊到每个上课日，更贴近实际经营视角。

## 九、产品指标体系（建议监控）

| 指标 | 定义 | 目标 |
|---|---|---|
| 约课完成率 | 签到数 / 预约数 | > 75% |
| 会员月活率 | 当月有约课的会员数 / 总会员数 | > 40% |
| 次数卡耗卡率 | 已消耗次数 / 初始次数（全量） | > 60% |
| 期限卡到课频次 | 期限卡持卡人月均上课次数 | > 8次/月 |
| 满员率 | 满员时段数 / 总时段数 | 20-50% 健康区间 |
| 爽约率 | 预约后未签到且未取消 | < 15% |
| 馆长操作时长 | 每天后台操作时长（效率指标） | < 30分钟/天 |
